# Phase 5 ML Methodology

## Objective

Build a reproducible three-class classifier that predicts how well a freelancer
matches a project:

- Strong Match
- Moderate Match
- Low Match

The model is a `RandomForestClassifier` trained on synthetic, feature-driven
labels. It is integrated into the existing FastAPI backend through a cached
service and two endpoints.

## Why synthetic data

The application does not contain a large, consented, historically labelled
matching dataset. Using applications or hiring outcomes as labels would also
introduce future-information leakage. The Phase 5 dataset is therefore
synthetic and explicitly documented as such.

The synthetic-data metrics in `ML/reports/evaluation_report.md` measure how well
the model learns the rubric on synthetic records. They do **not** establish
real-world matching accuracy.

## Dataset generation

Script: `ML/scripts/generate_dataset.py`

1. Sample a project category, 2–7 required skills from that category, and an
   experience level.
2. Sample a latent fit value from `Beta(2.2, 2.2)`. This latent value is used
   only to create realistic correlations; it is never saved as a feature or
   used directly as a label.
3. Build a freelancer profile whose skills, years, rating, portfolio and work
   history are correlated with the latent fit, with noise and occasional
   inconsistency.
4. Extract the eight model features using the same `ML.features` function used
   by the backend.
5. Apply the transparent rubric to create `match_score` and the label.
6. Reject duplicate feature vectors (rounded to four decimals) and repeat until
   1,500 unique records are produced with seed 42.

The generator uses no application status, hiring outcome, or post-decision
information.

## Label rubric

The weighted rubric is:

| Feature | Weight |
|---|---:|
| `skills_match_percentage` | 30% |
| `required_technology_match` | 20% |
| `category_relevance` | 15% |
| `years_experience` | 10% |
| `experience_level_compatibility` | 10% |
| `avg_rating` | 10% |
| `portfolio_evidence` | 3% |
| `work_history_evidence` | 2% |

Thresholds:

- Strong Match: score `>= 75`
- Moderate Match: `50 <= score < 75`
- Low Match: score `< 50`

The rubric is implemented in `ML/features.py::compute_match_score()` and
`label_for_score()`.

## Training and evaluation

Script: `ML/scripts/train_model.py`

- Load and validate the CSV: required columns, no nulls, known labels, valid
  ranges, and no duplicate feature vectors.
- Use only the eight numeric features as `X`; `match_score`, metadata columns
  and the label are not model inputs.
- Stratified 80/20 train/test split with `random_state=42`.
- Pipeline: `SimpleImputer(strategy="median")` then
  `RandomForestClassifier(n_estimators=300, max_depth=12, min_samples_leaf=3,
  class_weight="balanced_subsample", random_state=42)`.
- 5-fold stratified cross-validation on the training split.
- Test metrics: accuracy, macro/weighted precision, recall and F1, per-class
  metrics, confusion matrix and classification report.
- Feature importance from the fitted Random Forest.

The imputer is inside the pipeline, so it is fitted only on the training data
and each cross-validation training fold. The test split is not used for
preprocessing or model selection.

## Model artifact

- Model: `ML/models/match_model.joblib`
- Metadata: `ML/models/model_metadata.json`
- Version: `phase5-rf-v1`
- Format: Joblib-serialized scikit-learn `Pipeline` containing the imputer and
  Random Forest.

The backend loads the Joblib model once through a lock-protected singleton in
`Backend/services/ml_service.py`. Startup calls `warm_model()`; a missing model
is logged and ML routes return `503` instead of stopping the API.

## Backend integration

### `POST /ml/predict-match`

Authenticated users only. The request contains only `freelancer_id` and
`project_id`. The server:

1. Loads the public freelancer profile and project.
2. Extracts the eight features with the shared extractor.
3. Calls the cached model once.
4. Computes `rubric_score` with the same transparent `compute_match_score()`
   used to generate the synthetic labels.
5. Returns the predicted label, rubric score, class probabilities,
   predicted-class confidence, internal expected ranking score, model version
   and feature evidence.

The request schema uses `extra="forbid"`, so a client cannot submit feature
values or a label as if they were model output.

### `GET /ml/projects/{project_id}/matches`

Client-only and owner-only. Scores up to 500 public freelancer profiles and
returns the top `limit` results sorted by `expected_match_score`. Each item
includes `label`, `rubric_score`, `confidence` and class probabilities. The
response uses `FreelancerPublic`, which excludes email, password hashes and
`user_id`.

## Missing data and failure behavior

- Missing freelancer profile or project → `404`.
- Invalid ObjectId → `404` with a not-found message.
- Missing model artifact → `503`.
- Missing optional profile fields → zero evidence, not an exception.
- No project skills → match percentages are `0.0`.
- Unknown or `Other` project category → `category_relevance = 0.0`.
- Missing experience level → neutral compatibility `0.5`.

## Frontend contract

`Frontend(2)/js/api.js` calls `POST /ml/predict-match`. `Frontend(2)/js/ui.js`
uses `label` as the predicted class, `rubric_score` as the fit score, and
`confidence` as a separate predicted-class probability. The legacy
`match_percentage` field remains in responses only for compatibility and is
documented as `confidence * 100`, not a match-quality score.
`expected_match_score` remains an internal ranking score.

All match chips and panels use the same `readMatch()` mapping, so freelancer
dashboards, client dashboards, project cards, applications and applicant views
present the three values consistently.

No `/v1/models` route or call exists in this repository. That path belongs to
the Gemini/Google API family and is unrelated to the matching model; the
intended ML integration is the existing `/ml/predict-match` call. Generative AI
integration remains out of scope for Phase 5.

## Limitations

- Synthetic labels are rubric-generated; the model partly learns the rubric.
- The synthetic dataset is not a representative sample of real freelancers or
  clients.
- Reported metrics are not evidence of real-world accuracy or fairness.
- The model does not use free-text semantic embeddings; it uses structured
  skills, portfolio technologies and keyword evidence.
- Ranking is capped at 500 candidate profiles for predictable request cost.
- The confidence value is the maximum class probability, not a calibrated
  real-world probability.
- `rubric_score` is deterministic from the live features and may disagree with
  the model's predicted label. It is not a calibrated probability either.
- The model should support, not replace, human hiring decisions.
